## 中文原文（verbatim）

Jev火了。前OpenAI研究员创办的TypeSafe，推出了一个不生成自由文本、专门做判断的模型。官方公布的响应时间是70—500毫秒，每百万输入token收费0.042美元，输出免费。开发者的反应也很有意思：有人嫌它只是重新包装了分类器，有人已经拿它做产品。

Jev的用法很直接：把材料、问题和候选交给它，它返回选择、评分和概率，程序拿到结果就能继续执行。问题和选项可以按任务定义。常见聊天模型要逐个生成token，Jev可以围绕同一份材料，并行回答多个独立问题。分类、筛选、路由、质量检查，都是它瞄准的工作。

训练方法叫"面向校准决策的强化学习"，简称RLCD。它追求的是让模型报出的把握程度尽量符合实际准确率，方便程序决定直接执行，还是交给更强的模型或人复核。这个目标很重要，但具体做到了什么程度，还需要更多公开验证。

争议也集中在这里：分类和结构化输出早就有了，Jev到底新在哪？已经有开发者用Qwen做出了类似的并行判断实现。但相似接口不等于复现了Jev的训练和判断质量。至于官方宣传的"零幻觉"，保证的是输出符合预设格式，答案照样可能错。

推荐看看开源项目browser-use/jev-ultrafast。程序先把网页上的按钮、输入框整理成动态候选，Jev选择操作和目标；需要填写城市名称等文字时，再调用文字模型生成，由代码执行。页面变化后，候选随之更新，没有提前写死每一步怎么点。

项目展示了约7秒完成一次机票搜索，Jev单次调用的延迟中位数为178毫秒。7秒不含初始页面准备和独立的事后验收，也没有购票。仓库公开了代码、运行方法和性能记录，配置Jev与文字模型的API密钥后，可以按说明尝试，并查看每一步的选择和执行记录。

我更看好这类模型降低Agent的高频判断和检查成本。调用足够快、足够便宜，才有条件在执行过程中多确认几次，而非等整个任务跑完才发现做错了。分类和打分没有多新鲜，但能以什么成本、什么速度放进真实软件，很重要。Jev未必需要证明自己是一场架构革命，先把这些工作做得好用，就有价值。

## Key Takeaways

### 1. Jev 是什么

| 维度 | Jev | 传统 LLM |
| --- | --- | --- |
| 输出 | 选择/评分/概率（固定格式） | 自由文本 token-by-token |
| 延迟 | 70–500ms（中位 178ms） | 数秒级 |
| 定价 | $0.042/M input tokens，输出免费 | 按输出 token 计费 |
| 并行 | 同一材料并行回答多个独立问题 | 通常单线程生成 |
| 目标场景 | 分类/筛选/路由/质量检查 | 对话/生成/推理 |

### 2. 训练方法：RLCD
- **RLCD** = Reinforcement Learning for Calibrated Decisions
- 核心目标：让模型报出的**置信度 ≈ 实际准确率**
- 程序据此决定：直接执行 vs 交给更强模型/人复核
- 校准价值 > 绝对准确率

### 3. 争议焦点
- **反方**：分类和结构化输出早有了，只是重新包装分类器
- **正方**：相似接口 ≠ 复现了训练和判断质量；Qwen 已有人做出类似实现
- **零幻觉**：保证输出格式符合预设，答案仍可能错
- 关键问题：**成本/速度/可靠性**能否放进真实软件

### 4. 开源集成案例：browser-use/jev-ultrafast
- **架构**：Jev 选择操作和目标（动态候选）+ 文字模型生成具体文本 → 代码执行
- **动态候选**：页面变化后候选随之更新，不硬编码每步
- **性能**：机票搜索约 7 秒完成（不含初始页面准备和事后验收）
- **公开程度**：代码、运行方法、性能记录全部开源

### 5. 核心洞察（作者观点）
> Jev 的价值不在于是不是架构革命，而在于：
> **把高频判断和检查成本降下来** ——
> 调用足够快、足够便宜，才有条件在执行过程中多确认几次，
> 而非等整个任务跑完才发现做错了。
